How to use it

From upload to verified findings in six steps

Everything below runs against the live deployment: hosted Postgres seeded with CUAD, the Next.js dashboard, and Claude for extraction.

Sign in

Use the demo account above, or create your own with a real email address and confirm it.

Browse or upload

Open Contracts for the seeded CUAD corpus, or Upload a plain-text (.txt) contract up to 2MB.

Review the extraction

Uploads run live extraction for the ten tracked categories. The detail page shows a clause checklist beside the full source text.

Check risk flags

The Risk Flags tab lists policy deviations ranked by severity: info, warning, or critical.

Inspect accuracy

Eval Metrics shows precision, recall, F1, hallucination rate, and abstention accuracy per category.

System design

How the pieces fit together

A TypeScript monorepo deployed across three platforms. The dashboard and the REST API share one set of packages, and every write lands in Supabase. Hover or tap a component for details.

Request path
upload → extract → ground → flag
An upload goes from the dashboard's route handler into the extraction package, which asks Claude for verbatim quotes, grounds each one against the source, then hands the clauses to the risk engine. Clauses and flags are written to Supabase, and the dashboard reads them back with Server Components.

How it was built

A six-stage pipeline, each stage measurable

Built bottom-up from a ground-truth dataset, so every layer could be checked before the next one depended on it.

01

Ingest

CUAD parsed into Postgres with a repeatable seed.

02

Chunk + embed

Offset-preserving chunks embedded into pgvector.

03

Extract

Claude tool use, validated by shared Zod schemas.

04

Ground

Quotes re-found in source, or the clause is rejected.

05

Assess risk

YAML policy rules produce severity-ranked flags.

06

Evaluate

Scored against CUAD expert labels per category.

The model quotes; the code locates

Claude is asked for a verbatim quote, never for character positions. The grounding guard searches the source for that quote itself and only then records offsets, which is why the clause highlight in the dashboard is always exact.

// packages/extraction/src/grounding.ts exact match → offsets normalized match → offsets // whitespace-tolerant no match → rejected // abstain, don't guess

Policy as configuration

Compliance rules live in policy/default.yaml, so an organization can tighten a rule without touching application code.

Key features

Designed for reviewers who need to trust the output

Grounded citations

Every extracted clause maps to an exact character span. If a claim can't be grounded, the system abstains.

Quantified accuracy

Precision, recall, F1, hallucination rate, and abstention accuracy against CUAD expert labels.

Configurable risk policy

Acceptable ranges per clause type live in YAML, so rules change without a code change.

Domain-specific retrieval

Legal-domain embeddings plus exact clause-type matching for hybrid retrieval over long documents.

Type-safe pipeline

Shared Zod schemas enforce one source of truth across ingestion, extraction, and the API.

Single-language stack

TypeScript across frontend, backend, and shared packages keeps the system easy to reason about.
